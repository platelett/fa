# CCE FP32：精度提高后，重新设计空间与调度

这个版本希望保留 Cube 的 FP16 矩阵乘法速度，同时让 Vector 的主要中间计算使用 FP32。输入和最终输出仍是 FP16，Cube 与 Vector 之间的分数、权重和输出贡献也仍是 FP16。

目的很具体：输出还没归一化时，累加值可能很大。FP32 累加能容纳更大的范围，中间统计和指数运算也有更高精度。它不是把最终输出简单转成 FP32。

Cube 是矩阵乘法单元，Vector 是向量计算单元。这条路线沿用 [FP16 版的 Cube 流水](cce-fp16.md)，主要重设计 Vector 部分；attention 的基本过程见[总览](README.md#先知道-attention-在做什么)。

最终最大输入用时 **793.552 ms**，比 FP16 版本慢，但比第一版 FP32 明显改善。最重要的两步是重新分配片上空间，以及把 Vector 的依赖等待安排好。

## 1. 直接扩大精度，空间会先成为问题

第一版仍希望让 O 留在片上。一次处理 Q512 时，每个 Vector 上的 FP32 O 就要 **128 KiB**。而 Vector 的片上存储总共只有约 192 KiB 可供这套实现规划。

O 放下了，不等于流水也放下了。剩余空间还要装输入、输出、FP32 工作数据、归约中间值和多代缩放系数。

为了塞进去，第一版共用一些输入输出空间，并把完整 key 块拆成更小的内部计算片。这样能正确计算，但限制了下一块加载、当前块计算、上一块写回的重叠。

它还做了初步调度优化，例如把权重转回 FP16 放在求和归约的两层之间。收益有限。最大输入最快的第一版在后续对照中约为 **1100 ms**，没有保住 FP16 的速度。

## 2. 先把空间留出来，再谈指令优化

第二版把同时处理的 Q 批次缩到 **256**。每个 Vector 处理其中 128 个 query，FP32 O 只需要 **64 KiB**。

省下的空间用于完整计算块和独立搬运队列。一次 S/P 搬运仍是 **16 KiB FP16**，转成 FP32 后的工作数据是 **32 KiB**，不再为了省空间把这个计算块拆小。

主要空间分配如下；数值是两个 Vector 中每一个的占用。

| 用途 | 大小 | 为什么需要 |
|---|---:|---|
| 输入队列，两个槽 | 32.5 KiB | 两份 16 KiB 载荷，另含布局空隙；当前输入计算时可加载下一份 |
| 输出队列，两个槽 | 32 KiB | 当前计算时可写回上一份，不占输入槽 |
| FP32 O 累加 | 64 KiB | 所有 key 块处理完前不往返外部内存 |
| FP32 工作区 | 32.25 KiB | 保存一个完整转换、缩放、指数计算块 |
| 两块归约区 | 24.5 KiB | max/sum 的中间结果独立存放，交替推进 |
| 系数与统计等 | 3.75 KiB | 保存缩放后的最大值、分母和多代系数 |
| **合计** | **189 KiB** | 留在实现的片上预算内 |

这一步的关键是输入和输出各有自己的两个槽。加载器与计算代码拿到的不是一个裸地址，而是“地址 + 对应锁”。槽正在计算时不能被 DMA 覆盖，槽正在写回时不能被下一次计算重写。

O 自己还有固定身份：第几份输入槽，不能决定更新哪一片 O。临时搬运槽轮换，输出对应的 query 范围不轮换。

## 3. 高精度不意味着所有步骤都要扩大到 FP32

Cube 已经把 S 传成 FP16。对这些数求最大值，用 FP16 比较不会丢失额外精度，所以最大值树保留 FP16。

得到块最大值后再转成 FP32，保存已经缩放的运行最大值。分数缩放、减最大值、指数、权重求和、跨块系数、分母和 O 更新都使用 FP32。

求和读取的是**尚未舍入回 FP16 的指数结果**。之后把权重 P 转回 FP16，交给 Cube 做 PV。FP32 中间计算仍无法消除 FP16 通信本身的范围限制。

输出更新也不必先把整块 FP16 输出贡献展开成 FP32 临时张量。采用两步：先把 FP32 O 乘缩放系数，再用混合精度加法直接加入 FP16 的输出贡献。代码对应 `VMUL + VAXPY`。

这样避免了一份较大的转换临时区，也让空间设计更容易保持完整搬运块。

## 4. 用必需的转换工作填补归约等待

归约是一棵树：先两两比较或相加，再合并上一层结果。后一层要等前一层写完，最后几层工作很少，等待就更容易露出来。

FP32 版本恰好有两项无论如何都要做的工作：

- max 树运行时，把原始 S 从 FP16 转成 FP32。
- sum 树运行时，把指数结果转回 FP16 的 P。

把这些工作放在两层归约之间，可以在等结果时做正事，而不是纯粹停下来。

前提是归约区不能与转换工作区重叠。否则 max 还没用完的结果，会被 S 转换覆盖；或者为了保护它，只能推迟转换，失去插入工作的机会。这也是第二版重新排地址、让两块归约区独立的原因。

第二版与第一版最快配置的匹配对照：

| Batch / Length | 第一版，ms | 第二版，ms | 用时下降 |
|---|---:|---:|---:|
| 2 / 131072 | 1100.208 | 872.480 | 20.70% |
| 2 / 65536 | 275.456 | 219.549 | 20.30% |
| 1 / 32768 | 34.796 | 27.977 | 19.60% |

这约 20% 的改善属于整套空间与调度重设计，不能全部算到某一条混合精度指令头上。

## 5. 第三版去掉 Vector 全流水等待

第二版仍在归约的若干层之间使用 `BAR.V`。它让 Vector 前面的工作全部完成后再继续，安全但可能等得过多。用户要求完全禁止它，第三版于是研究具体依赖，而不是每层都做一次完整等待。

第一种尝试很机械：把每个等待换成相同数量的空描述符。给足间隔可以正确运行，却约慢 **11%–13%**；一律缩短间隔，又出现 max/sum 数值错误。

最终选择按实际读取路径安排：让较长的前一层遍历提供一部分间隔，把必要转换与缩放放进短依赖之间，某些小统计值到整个通信块的消费者那里再等待，并在最后读者完成后尽早归还临时空间。

仍然没有被有用工作覆盖的短依赖，保留经过验证的空描述符间隔。**没有 `BAR.V`，不等于没有依赖或没有任何等待。** 这些间隔属于当前布局和指令顺序，不能当作通用硬件周期数。

同一普通 NZ 配置的第二版、第三版对照：

| Batch / Length | 第二版，ms | 第三版，ms | 用时下降 |
|---|---:|---:|---:|
| 2 / 131072 | 872.479 | 793.489 | 9.05% |
| 2 / 65536 | 219.545 | 199.845 | 8.97% |
| 1 / 32768 | 27.975 | 25.505 | 8.83% |

普通方向各配置改善约 9%。转置方向却慢了约 6.5%，它不能直接套用普通方向更短的依赖间隔。公开版本选择的是最快的普通 NZ 配置，不把“去掉 barrier”写成普遍加速规律。

## 最终版本与还没解决的问题

公开版本使用 Q256、K512、普通 NZ、K-first，FP32 O 驻留片上。最终统一测试为 **793.552 / 199.889 / 25.524 ms**，输入从大到小。

Q256 下，某些原来的八种配置变成相同几何，实际只有五种不同程序。因此不能把八个名字当成八次独立优化成功。

Vector 仍然是主要研究对象：第三版最大输入中，Vector 忙碌时间约 789 ms，Cube 矩阵乘法约 562 ms。去掉 `BAR.V` 缩小了差距，但还不能说 Vector 已经达到理论算术吞吐率。剩余的转换、指令发射、依赖和内存访问需要进一步分辨。

最值得借鉴的是第二版的顺序：**先确保完整计算块、独立输入输出双缓冲和必要临时区都放得下，再安排指令来填补等待。** 一个勉强塞满片上空间的版本，往往没有余地实现高效流水。
