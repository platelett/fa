# CCE FP16：让整条流水跟上矩阵乘法

这条路线最终把最大输入的完整 attention 做到 **572.472 ms**，约为本机 25 个 Cube 名义峰值的 **97.3%**。一路上最重要的变化，是减少不必要的布局转换、等待和中间数据搬运。

早期只研究“分数 → softmax → 输出贡献”，还没有把所有输出贡献合成最终结果。后来加入输出累加与归一化，才成为完整 attention。读历史成绩时，需要先区分这两个阶段。

下面的 Cube 做矩阵乘法，Vector 做 softmax 和输出更新。Q、K、V 与在线 softmax 的含义见[总览](README.md#先知道-attention-在做什么)。

## 1. 从四种排列开始，把变量分开

第一次系统比较有四种组合：分数按 query×key 或 key×query 排列，再各自比较先遍历 query 小块还是 key 小块。矩阵乘法和 Vector 每次处理的数据量尽量保持一致。

为什么要比这些？同一个数学表达式，可以有不同的数据存储和遍历顺序。它们改变输入能复用多久、数据是否连续、Vector 什么时候拿到第一块结果。

这里逐渐分清了两个尺寸：

- **一次驻留多少 query**：这一批 Q 留在 Cube 的片上输入缓存 L1 中，遍历 key 块时复用。
- **一次交给 Vector 多少 query**：更大的驻留批次还可以切成小块，边算边交接。

两者不必相同。后来的代码分别叫 `Q_L1_LEN` 和 `WS_Q`，key 通信宽度叫 `WS_K`。逻辑上先处理一批驻留 Q 与一个 key 块，再在内部切小块；不能为了内部循环方便，悄悄改变这一层顺序。

## 2. 转置版本慢四倍，问题在“怎么搬”

早期转置版的算术量与普通版相近，运行时间却差得很远。关掉 max/exp 后，它仍然很慢；把搬运改宽，速度才明显改善。

原因是普通的转置矩阵存储，让 Vector 想取的一小组 query 分散在许多行里。读取一个 16 KiB 计算块，要发出大量只有 32 字节的窄条搬运。

解决办法是保留 Cube 的原生分块格式 **NZ**。可以把它理解成“按计算小砖块存储”，而不是按普通矩阵的整行存储。转置版采用 `[Q/16, K, 16]` 排列，同一组 query 的数据更适合整块搬运，不需要另做一次全矩阵转置。

当时同轮小规模比较中，密集转置版约 **123.138 ms**，改后的转置版约 **30.293 ms**，普通版约 **31.283 ms**。差距主要随搬运组织方式改变，而不是随是否计算指数改变。

后来也给普通方向补上 NZ 模式。Vector 按小砖块直接做 softmax，PV 再直接加载这种布局。在当轮比较中，普通 NZ 的 Q-K-Q 配置比普通行式布局约快 **6.5%–7.7%**。

这一步形成三类布局：普通行式、普通 NZ、转置 NZ。它们的归约树不同，但都处理完整的 16 KiB 数据块。

## 3. 小块更好流水，大块更好写出，怎么兼顾

Cube 的计算结果先放在片上结果缓存 L0C，再由专门的 FIX 单元导出。曾希望每算好一个 128×128 小块就写出，让写出更早开始。

但写到普通矩阵中时，小块可能只覆盖每行的一小段。这样的跨行写出，不能只用“总共写了多少字节”判断效率；行宽、步长、首地址和结果产生顺序都重要。

因此专门做了独立实验：比较连续与跨行写出、128×128 与 128×256、两种结果产生方向，以及是否使用 **UnitFlag**。UnitFlag 允许 FIX 随结果就绪推进，不必先等整次矩阵乘法完成。

最后验证了一个实用组合：**两次 128×128 矩阵乘法写入 L0C 的两个不同半区，配一次 128×256 导出。** 计算仍分小块，导出保持较宽的几何形状。输入缓存也能分半使用，一半正在被计算读取，另一半准备下一次输入。

随之去掉了原来每个小块后过强的“等 FIX 完再继续乘法”依赖，让矩阵乘法和导出有机会重叠。仍保留实际需要的保护，不能提前覆盖尚未读完的结果。

也试过先把结果放进 L1，再整块写到外部内存。它没有成为这条路线的解决办法：原生 NZ 中转没有测出稳定收益，而期望的普通矩阵转换在测试通路上实际仍得到 NZ 排列，无法按原计划拼出普通矩阵。

## 4. 不只改加载顺序，还要把锁与数据块对齐

起初一些输入按“大块”准备，实际计算却按小片消费。V 尤其明显：PV 一次只需要其中一个 128×128 面板，提前搬完整个大块并不总是合适。

后来的办法是按实际消费顺序分片加载。搬运单元各自顺序推进指令；正常代码只要把后续独立工作排出来，就能自然提前执行，不必另堆一套远距离预取。

但只调指令顺序还不够。假如 V 的四个面板共用一个“大块空闲”信号，即使下一片对应的地址没人使用，也可能被前一片阻塞。因此改成**每个独立面板有自己的所有权**。K、P 和 L0 半区也检查同样的问题。

归还时机也要精确：某块数据的最后一次读取结束，就可以归还；不用等整轮 PV 或另一个无关搬运结束。对于两个独立的只读消费者，则等双方都读完后，再允许下一次写入。

“加载顺序等于消费顺序”也不是唯一序列。一次乘法的两个输入都要到齐，它们谁先加载都满足这句话，却可能产生不同等待。于是把 L1→L0 和外部内存→L1 两层一起考虑，同时检查哪个半区更早空闲。

最终保留的是分片所有权和选中的简单顺序，没有把所有调度尝试堆成运行时分支。

这些规则后来也整理成可复用 header：锁和跨核交接、数据搬运、任务划分、缓冲槽与归约辅助函数。FA 自己的算法保留在 QK、softmax、输出更新等文件里。这样共享的是数据使用规则和常用操作，不必把整个 attention 搬进公共库。

## 5. 从四种组合走到八种，参数不再只代表块大小

进一步比较时，普通方向分成三种复用方式：

| 名称 | 直观含义 |
|---|---|
| Q-first | 固定一个小 Q 块，让它和这一轮的 K 小块逐个计算 |
| K-first | 固定当前 K 小块，让它服务整批驻留 Q |
| Q-K-Q | 先切一组 Q，再在组内换 K 小块和 Q 小块，折中通信大小与复用 |

普通行式与普通 NZ 各有这三种，转置 NZ 保留两种，共 **3+3+2**。转置 Q-K-Q 当时没有找到有竞争力的配置，暂停实现。

这些版本的目标是共用算法代码，由参数选择布局和顺序。参数扫描尝试了不同 Q 驻留长度、通信 query 数和 key 宽度，容量不够的组合跳过；768-query 批次还要处理最后不足一批的部分。

两个原始预期值得保留：小通信块能更早启动流水，但会增加片上搬运；更宽 key 块能减少输出贡献回传与合并的次数。第二个预期在尚未实现输出合并的早期实验中无法检验，不能拿那时的扫描成绩替它下结论。

## 6. 一批核拖到最后，增加可调度的小任务

即使每个核内部的流水不错，整个 kernel 也可能等少数慢核结束。固定把长任务分给少量核，会让这种尾部等待更明显。

于是把完整的驻留-Q 任务分成许多逻辑 block，供设备接续调度。这里仍是**一次 kernel launch**，不是发几千次 kernel。每个 query 的完整 key 遍历留在同一个任务内。

同时检查任务边界，避免上一批完全排空后才开始下一批的独立工作。更多任务也会增加初始化和切换开销，因此一路测到最细可用粒度，而不是先假定 192 个任务已经足够。

在这一阶段，转置 NZ 的同轮对照约快 **8%–12%**，最大输入达到约 **573 ms**。这是还没有输出合并的诊断路径，不能与最终完整 attention 的数值直接解释成同等工作量。

多逻辑 block 后来被保留。公开仓库默认使用 24 组；首页性能使用本机已验证的多任务模式，覆盖 25 个 Cube，运行时需显式启用。

## 7. 加入完整输出，速度为什么又掉了

之前每轮只产生一个输出贡献。完整 attention 还要把它合进运行中的输出，并在最后除以权重总和。

这不是简单相加：在线 softmax 的最大值更新时，旧的输出和旧的权重总和也要乘同一个缩放系数。这些系数必须按代保存，因为 softmax 往往已经向前跑了几块，输出合并还在处理旧块。

首先修正了输出贡献环：它必须按**完整通信块**准备足够的槽，不能把整块信号和少量半块槽混用。旧协议有额外限流，能正确运行，却让某些大通信块在内部反复等空槽。修正后，一些 K-first 配置约快 **27%–33%**。

随后重写最大值和求和归约。旧求和频繁等待前一次累加完成；新版用两块独立归约区交替推进。普通 NZ 搬进片上后在中间留一个小空隙，调整对应输入的地址相位。独立转换等工作放在依赖层之间，减少空等。

还把输出贡献搬运扩到 16 KiB，补全运行中输出的读后写、写后读保护。单核专用的外部临时区域同样需要表达使用区间，不能只保护片上搬运槽。

这些步骤改善了正确性和调度，但最主要的后期损失仍然存在。

## 8. 真正的大收益：输出累加一直留在片上

当时运行中的输出 O 每轮都要读回来、更新、再写出去。去掉这条搬运路径的诊断实验明显变快；只去掉相应算术，没有同样效果。

一个更直接的设计是：**缩小同时处理的 Q 批次，让 O 放进 Vector 的片上存储 UB，直到最后才写出。**

Q 变小会多读几遍 K/V，因此并非没有代价。但省掉每轮的 O 读写后，整体更快。相同 Q512 几何的对照中，流式 O 约 **624.553 ms**，片上 O 约 **583.626 ms**，下降 **6.55%**。与当时完整 attention 版本的三规模对照，整体约快 **8%–9%**。

按逻辑搬运量计算，在原有 S/P 读写之外，完整输出处理原先增加约 37.5% 的 Vector 搬运；O 驻留后只剩输出贡献读取，增加约 12.5%。最终输出写回另计。

重要的是，这个设计并不要求把输出更新硬插进 softmax 的内部。省掉不必要的往返，流水结构也更清楚。

## 9. 最后的选择：Q768、普通 NZ、片上 O

片上 O 的方案随后扩展到所有布局和复用方式，再调整输入槽组织，让更大的 Q 批次也能放下。最后重新枚举 QK 和 PV 的两种结果产生方向，而不是继承早期方向选择。

普通 NZ 的 Q-K-Q 配置在这一步从约 **580.441 ms** 改善到 **573.687 ms**。方向改变的是结果在哪些位置先就绪，影响 FIX 如何跟上；Vector 算法没有随它改变。

最终公开版本选择：驻留 **768 个 query**，每个通信块 **256 query × 512 key**，O 使用 FP16 并留在片上。它使用当前测定的 QK=N、PV=M 方向，四个输入槽，以及分片的输入和锁。

后面还测了原生 NZ 输出累加布局、P 的两个读者并行、槽深度、批量输出更新和进一步顺序调整。有些在个别模式上有效，但没有继续稳定加速最终最快配置。因此没有把这些选项全部叠进去。

真正保留操作数的蛇形遍历也测过：它能少搬 Q，但没有稳定换来同等幅度的整算子收益。只改变缓冲编号的“格雷码”不属于这个优化，不能用它的失败否定真正的数据复用。
