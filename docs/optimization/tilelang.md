# TileLang：先搭好流水，再确认哪里值得优化

这条路线的目标，是用 TileLang 写出完整的 attention，并让矩阵乘法、softmax 和内存搬运尽量同时进行。它比直接写底层指令更容易表达算法，但生成代码的效果也依赖编译器和算子接口。

下面的 Cube 指矩阵乘法单元，Vector 指负责 softmax 和输出更新的向量单元。attention 的三道工序见[总览](README.md#先知道-attention-在做什么)。

目前保留的是 `tl_stream_v3`，使用三个工作区槽。最大输入的统一实测用时为 **1118.169 ms**。它不是下文某个旧编译环境下结果的直接延续；公开前，已经在指定的 TileLang PR #1852 上重新测试。

## 1. 先把整张分数矩阵拆成流水

长序列 attention 的分数矩阵很大。v3 的基本办法是：Cube 算一块分数，Vector 处理这一块的 softmax，然后 Cube 用权重计算输出贡献，Vector 再更新输出。

为避免双方总在等对方，工作区准备多个槽。一个槽正在被 Vector 使用时，Cube 可以处理另一个槽。在线 softmax 保存运行中的统计量，最后得到已经归一化的完整输出。

这条并行流水是后面所有实验的基础。更早版本的完整演变记录已经不齐，不能补写一条看似连续的 v1 到 v3 故事。

## 2. 块做得更大，为什么没有更快

最直观的想法是：一次多处理一些 key，少循环几次，应该能省掉调度开销。

当时把 key 分块从 1024 扩到 2048，也尝试增加每块的 query 数量。结果没有得到收益：扩宽 key 块约慢 **5%–8%**，增加 query 行数大体持平，更大的组合还碰到片上空间和接口限制。

原因可以这样理解：更大的块减少了次数，也让每次处理变长，消耗更多片上空间，还可能增加某些输入的重复加载。softmax 对每个分数做的指数和归约并没有消失。减少循环次数，不等于减少主要工作量。

因此保留原来的分块，接下来查流水中的各部分各自要多久。

## 3. 关掉一部分计算，才能看清重叠关系

实验先后去掉 Cube 计算、Vector 计算、内存搬运，以及 softmax 或输出更新。去掉的部分仍保留必要信号，目的是诊断，输出当然不再是正确的 attention。

这一步纠正了一个重要误判：**删掉某项工作后只快一点，不代表那项工作只花了这么一点时间。** 它可能原本就和另一项工作同时进行。

早期对照中，只留下 Cube 的用时约为完整版本的 79%；只留下 Vector 计算的用时约为 81%。双方都不便宜。profiling 也看到，一起运行时，若干内存搬运路径比单独运行更慢。

这说明要同时看两件事：Vector 本身的计算，以及它与 Cube、搬运单元配合后的整体进度。不能把各个单元的忙碌时间相加，也不能把删掉一个组件得到的差值直接当作它的独立成本。

这些观察来自当时的融合 softmax 版本，用来解释这一步为什么改变了优化方向。它们不是对当前 PR #1852 版本重新做出的逐项归因。

## 4. 多给一个流水槽，有帮助；再加就不明显了

既然双方工作量接近，流水就需要留出足够的“周转空间”。两个槽可能让一方还没归还旧槽，另一方就等着使用它。

当时把槽数从 2 改成 3，三个输入规模上约快 **3%–4%**；增加到 4 没有继续得到明确收益。

这不是“缓冲越多越好”。缓冲只能让独立工作更早开始，不能消掉实际计算，也不能跳过数据依赖。到三个槽后，再加一个槽已经没有同样的效果。

## 5. 公开版本改用普通归约接口，然后重新比较

历史 v3 使用融合的 `SoftmaxFlashV2`。公开版本希望不额外引入这个接口，用户指定使用 [TileLang-Ascend PR #1852](https://github.com/tile-ai/tilelang-ascend/pull/1852)，其最大值与求和归约已经重构。

现在的 softmax 用几步普通操作组成：求最大值、减去最大值、计算指数、求和。跨块的统计更新和延迟的输出累加仍在。公开实现不需要另加融合 softmax 扩展。

接口和编译器改变后，不能照搬旧的“三个槽更快”结论。因此比较了相同环形实现的两个槽与三个槽，并检查不同代的缩放系数不会被覆盖。

| Batch / Length | 两个槽，ms | 三个槽，ms | 用时下降 |
|---|---:|---:|---:|
| 2 / 131072 | 1148.701 | 1125.264 | 2.04% |
| 2 / 65536 | 285.076 | 276.667 | 2.95% |
| 1 / 32768 | 35.650 | 34.511 | 3.20% |

三个规模都通过正确性检查，三个槽都更快，于是选入公开版本。随后最终源代码又参加四个 backend 的统一测试，得到首页的性能表。

## 最后保留了什么

保留 v3 的完整在线 attention 结构、三个工作区槽，以及 PR #1852 提供的普通归约接口。没有采用更宽 key 块，也没有把无法编译的历史精度实验写成成功优化。

这条路线最有用的经验是：先看各条流水独立和并行时的进度，再决定增加缓冲还是减少计算。换编译器或关键算子接口后，原来的性能选择要重新确认。

看代码可从 [TileLang 源文件](../../backends/tl_stream_v3/impl_tl.py)开始；这是可编辑的源文件，旁边的 `impl.py` 是生成产物。依赖版本和运行方式见[仓库 README](../../README.md)。
